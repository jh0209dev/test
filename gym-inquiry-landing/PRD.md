# 헬스장 문의 랜딩페이지 로컬 시제품 PRD

| 항목 | 내용 |
|---|---|
| 문서 상태 | 초안 — 로컬 시제품 구현 기준 |
| 작성일 | 2026-10-14 |
| 제품 범위 | 단일 헬스장 소개 페이지와 문의 관리자 화면 |
| 운영 형태 | 로컬 브라우저 테스트 전용 |

## 1. 제품 개요

### 배경

오프라인 전단지 홍보만으로는 잠재 회원을 모으기 어렵다. 헬스장 정보를 한 페이지에서 안내하고, 방문자가 간단히 문의를 남기는 흐름을 시제품으로 확인하고자 한다.

### 목표

1. 운동 초보자가 헬스장과 운동 환경을 이해할 수 있는 소개 페이지를 제공한다.
2. 방문자가 이름과 연락처를 포함한 문의를 작성하고 제출할 수 있게 한다.
3. 같은 브라우저에서 관리자 화면을 열어 문의를 확인하고 후속 관리 상태와 메모를 기록.

### 성공 기준

- 문의 폼 제출 결과가 같은 브라우저의 관리자 목록에 나타난다.
- 페이지를 다시 열어도 문의, 상태, 메모가 보존된다.
- 필수값 누락을 제출 전에 발견할 수 있고, 제출 결과를 방문자가 알 수 있다.
- 주요 화면과 동작이 모바일 및 데스크톱 폭에서 사용할 수 있다.

## 2. 사용자와 사용 맥락

### 주요 사용자: 운동 초보자

근처에서 운동을 시작할 헬스장을 알아보는 사람이다. 시설과 프로그램에 대한 구체 정보를 빠르게 파악하고, 전화로 바로 문의하지 않아도 연락처와 관심 내용을 남길 수 있어야 한다.

### 보조 사용자: 헬스장 운영자

시제품을 실행한 브라우저에서 관리자 페이지를 열어 테스트 문의를 확인한다. 문의 상태를 바꾸고, 상담 후 기억할 내용을 메모한다.

### 주요 사용 환경

- 방문자: 모바일 우선, 데스크톱에서도 이용 가능
- 운영자: 데스크톱 또는 모바일 브라우저
- 테스트 데이터: 가상의 이름과 연락처만 사용

## 3. 범위

### 포함

- 한국어 랜딩페이지와 문의 폼
- `/admin` 관리자 화면과 시제품 비밀번호 입력 단계
- 브라우저 `localStorage` 기반 문의 저장
- 문의별 상태 변경과 메모 저장
- 반응형 레이아웃, 필수값 검증, 제출 완료 피드백

### 제외

- 인터넷 공개 배포, 도메인 연결, 검색엔진 등록
- 서버 API, 데이터베이스, 클라우드 저장, 이메일·문자·카카오톡 알림
- 다른 브라우저나 기기 간 데이터 공유
- 다중 관리자, 역할 권한, 비밀번호 재설정, 정식 인증
- 문의 CSV 다운로드, 검색·필터, 대량 삭제
- 실제 가격·회원 후기·성과 수치 등 제공되지 않은 사실 정보

## 4. 사용자 흐름

### 방문자 문의 흐름

1. 방문자가 랜딩페이지에 들어와 소개와 운동 정보를 확인한다.
2. 문의 영역에서 이름과 연락처를 입력하고, 관심 운동과 문의 내용을 선택적으로 작성한다.
3. 필수 입력값이 모두 있으면 제출할 수 있다. 누락된 값이 있으면 해당 항목과 오류 안내를 보여준다.
4. 제출이 성공하면 완료 메시지를 표시하고, 문의를 현재 브라우저의 `localStorage`에 저장한다.

### 관리자 문의 관리 흐름

1. 운영자가 같은 브라우저와 사이트 주소에서 `/admin`을 연다.
2. 비밀번호 `1234`를 입력하면 관리자 문의 목록을 본다. 다른 값이면 오류 안내를 표시하고 목록은 열지 않는다.
3. 문의는 최신 접수순으로 표시한다. 운영자는 문의 내용을 확인하고 상태를 바꾸거나 메모를 작성한다.
4. 변경 사항은 즉시 같은 브라우저 저장 공간에 반영되며 페이지를 새로고침해도 유지된다.

## 5. 기능 요구사항

### 5.1 랜딩페이지

- 첫 화면에는 헬스장 이름, 한 문장 소개, 주요 문의 버튼을 둔다.
- 페이지는 다음 정보를 구분해 안내한다.
  - 헬스장 소개 및 초보자가 편하게 시작할 수 있다는 안내
  - 제공 프로그램 또는 운동 종류
  - 시설·기구 정보
  - 위치와 운영시간
  - 문의 폼
- 상호, 지역, 시설, 프로그램, 운영시간, 혜택이 미정이면 눈에 띄게 교체 가능한 예시 콘텐츠로 표시한다.
- 확인되지 않은 가격, 할인, 코칭 제공 여부, 후기, 회원 수, 운동 효과를 사실처럼 쓰지 않는다.
- 전화번호 등 실제 연락처가 제공되지 않은 경우 임의의 연락처를 만들지 않는다.

### 5.2 문의 폼

| 필드 | 필수 여부 | 동작 |
|---|---|---|
| 이름 | 필수 | 텍스트 입력 |
| 연락처 | 필수 | 전화번호 입력, 공백을 제외한 빈 값 여부 확인 |
| 관심 운동 | 선택 | 근력, 체중 관리, 체력 향상, 기타 등 일반적인 선택지와 기타 입력 지원 |
| 문의 내용 | 선택 | 자유 입력 |

- 제출 전에 이름과 연락처를 검증한다.
- 오류는 폼 가까이에 텍스트로 표시하고, 오류가 난 입력 항목을 식별할 수 있게 한다.
- 저장 성공 시 완료 메시지를 표시하고 중복 제출을 방지하기 위해 버튼 상태를 갱신한다.
- 로컬 시제품이며 실제 고객 정보를 입력하지 말라는 안내를 문의 영역에 표시한다.

### 5.3 관리자 화면

- 관리 경로는 `/admin`으로 제공한다.
- 화면 진입 시 비밀번호 입력 UI를 보여준다. 정답은 `1234`이며, 정답을 입력한 현재 페이지 사용 흐름에서만 관리 화면을 연다.
- 페이지를 새로 열거나 새로고침하면 비밀번호를 다시 입력하게 한다. 인증 상태를 영구 저장하지 않는다.
- 비밀번호가 틀리면 일반적인 오류 문구를 표시한다. 비밀번호 값 자체는 오류 문구에 포함하지 않는다.
- 문의 목록은 최신순으로 정렬하고, 이름·연락처·관심 운동·문의 내용·접수 시각·상태·메모를 확인할 수 있게 한다.
- 문의별 상태는 `신규`, `연락완료`, `등록`, `종료` 중 하나다. 새 문의의 기본 상태는 `신규`다.
- 상태 변경과 메모 저장은 문의별로 적용하고, 저장 결과를 화면에 반영한다.
- 문의가 없으면 빈 목록 안내와 랜딩페이지에서 테스트 문의를 작성할 수 있다는 안내를 표시한다.

## 6. 데이터 및 저장 요구사항

### 문의 레코드

| 속성 | 형식 | 설명 |
|---|---|---|
| `id` | 문자열 | 문의를 구분하는 고유 식별자 |
| `name` | 문자열 | 방문자가 입력한 이름 |
| `phone` | 문자열 | 연락처. 숫자 외 기호를 입력할 수 있으므로 문자열로 저장 |
| `interest` | 문자열 또는 빈 값 | 선택한 관심 운동 또는 기타 입력 |
| `message` | 문자열 또는 빈 값 | 추가 문의 내용 |
| `createdAt` | ISO 8601 문자열 | 문의가 접수된 시각 |
| `status` | 열거형 문자열 | `new`, `contacted`, `registered`, `closed` 중 하나 |
| `memo` | 문자열 | 운영자 메모, 기본값은 빈 값 |

- 저장소는 사이트 원점(origin)별 브라우저 `localStorage`이며 논리 키는 `gym-inquiries-v1`로 한다.
- 공개 폼과 관리자 화면은 동일한 원점의 저장소를 읽고 쓴다.
- 브라우저 프로필, 기기, 사이트 주소 또는 포트가 달라지면 저장 공간도 달라질 수 있다.
- 사이트 데이터 삭제나 브라우저 초기화 시 문의가 사라질 수 있다. 백업 및 복구 기능은 제공하지 않는다.
- 저장 실패나 데이터 파싱 오류가 발생하면 빈 목록으로 조용히 덮어쓰지 말고 사용자에게 오류를 알린다.

## 7. UX 및 시각 기준

- 전체 톤은 다크 차콜 배경과 라임 포인트를 사용하는 현대적이고 활기찬 스타일이다.
- 과한 장식보다 읽기 쉬운 제목, 짧은 문단, 명확한 문의 버튼을 우선한다.
- 초보자가 부담을 느끼지 않도록 전문 용어를 줄이고 구체 정보가 미정인 부분은 예시임을 표시한다.
- 모바일에서 폼 입력, 관리자 목록 확인, 상태 변경, 메모 작성이 가로 스크롤 없이 가능해야 한다.
- 입력에는 눈에 보이는 라벨을 붙이고, 오류와 제출 결과는 색상만이 아니라 텍스트로도 알린다.
- 키보드만으로 폼과 관리자 화면의 주요 동작을 수행할 수 있어야 한다.

## 8. 개인정보 및 보안 한계

- 이 시제품은 실제 문의 수집이나 고객 개인정보 운영에 사용할 수 없다. 테스트에는 가상 데이터를 사용한다.
- 비밀번호 `1234`는 클라이언트 화면 잠금 흉내이며, 소스와 브라우저에서 우회할 수 있다. 관리자 데이터에 대한 보안 경계로 간주하지 않는다.
- `localStorage` 데이터는 브라우저 프로필을 사용하는 사람에게 노출될 수 있다.
- 정식 공개 전에는 서버 측 저장, 접근 제어, 운영 가능한 관리자 인증, 개인정보 처리 안내 및 동의 절차를 별도로 설계해야 한다.

## 9. 수용 기준 및 확인 시나리오

1. **정상 문의 제출:** 이름과 연락처를 입력해 제출하면 성공 안내가 보이고 관리자 목록 최상단에 해당 문의가 나타난다.
2. **필수값 누락:** 이름 또는 연락처가 비어 있으면 저장되지 않고 누락된 항목을 안내한다.
3. **저장 유지:** 문의를 제출하고 페이지를 새로고침한 뒤에도 같은 문의가 관리자 목록에 남아 있다.
4. **다른 기기 격리:** 다른 브라우저 프로필이나 기기에서 제출한 문의는 현재 브라우저의 목록에 보이지 않는다. 이는 의도된 로컬 시제품 동작이다.
5. **관리자 잠금:** `/admin`에서 `1234` 입력 시 목록이 열리고, 틀린 값 입력 시 목록이 열리지 않는다.
6. **상태 저장:** 문의 상태를 변경하면 화면에 새 상태가 보이고 새로고침 후에도 유지된다.
7. **메모 저장:** 메모를 입력해 저장하면 해당 문의에 연결되며 새로고침 후에도 유지된다.
8. **빈 목록:** 문의가 없을 때 오류 화면 대신 빈 상태 안내가 표시된다.
9. **반응형 확인:** 모바일과 데스크톱 폭에서 주요 콘텐츠와 조작 요소가 겹치거나 잘리지 않는다.
10. **저장 오류:** 저장소 접근이 불가능하거나 데이터가 손상된 경우 오류를 명확히 표시하고 기존 데이터가 임의로 지워지지 않는다.

## 10. 운영 및 향후 전환

- 시제품은 로컬 개발 서버의 고정된 주소에서 실행해 랜딩페이지와 `/admin`이 같은 원점을 공유하도록 한다.
- 이 PRD는 로컬 시제품 구현에만 적용하며 공개 배포는 승인된 별도 단계로 둔다.
- 실제 온라인 운영을 시작하기 전에는 `localStorage` 구조를 서버 저장으로 전환하고, 관리자 접근을 서버에서 검증해야 한다. 클라이언트에 저장된 시제품 데이터는 서버로 자동 이전되지 않는다.
- 실제 상호·주소·운영시간·프로그램·가격·프로모션·연락처가 확정되면 예시 콘텐츠를 검토된 사실 정보로 교체한다.
